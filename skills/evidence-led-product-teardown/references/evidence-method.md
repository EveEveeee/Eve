# 证据准入与分析方法

## 1. 证据清单

每项证据记录：

| 字段 | 内容 |
|---|---|
| Evidence ID | 稳定编号，如 E01 |
| 来源类型 | 截图、录屏、页面、代码、日志、官方文档等 |
| 位置 | 截图号、URL、文件与行号、页面区域 |
| 时序 | 创建时间或操作顺序；未知则标明 |
| 可见事实 | 原文、按钮、字段、状态、资产、错误 |
| 支持结论 | 它能直接证明什么 |
| 限制 | 它不能证明什么 |

不要把同一截图拆成大量虚假独立证据；只有支持不同判断时才分项。

## 2. 完整性矩阵

深拆最低需要前五项，其余按用户目标决定：

| 证据面 | 最低可接受信号 | 缺失时的限制 |
|---|---|---|
| 产品对象 | 产品界面、代码入口或明确运行结果 | 无法确认分析对象 |
| 用户与目标 | 一条真实输入或操作 | 无法还原用户层 |
| 核心入口 | 起始页、表单、聊天或 API 输入 | 无法追踪任务起点 |
| 系统反馈 | 回复、状态、组件或事件 | 无法确认交互机制 |
| 结果/状态 | 真实资产、任务结果、错误或中断 | 不能声称流程完成 |
| 连续主流程 | 从输入到结果的大部分顺序 | 只能做局部拆解 |
| 修改流程 | 用户纠偏或版本变化 | 回退/局部重算未知 |
| 失败流程 | 错误、重试、余额、安全或中断 | 异常架构未知 |
| 模型信息 | 模型名、参数、结果或代码调用 | 模型层只能推断能力 |
| 数据信息 | 字段、实体、引用、代码或状态变化 | 数据层只能语义化设计 |
| 计费/权限 | 余额、套餐、授权或代码 | 只能标为未知/建议 |

## 3. 准入判定

- `READY_FULL`：核心流程连续，且用户要求的各重点有直接证据。
- `READY_PARTIAL`：足以拆某些层或阶段，但缺少失败、模型、数据等证据。只交付明确范围内的报告。
- `BLOCKED_EVIDENCE`：连产品对象、核心输入、反馈或结果都无法确认。只输出缺口和采集计划。

证据数量不是关键，覆盖面和连续性才是。大量相似截图不能替代任务起点或结果证据。

## 4. 三角验证

重要完成结论至少检查三个视角中的两个：

1. 对话/说明说了什么；
2. 任务或运行状态是什么；
3. 画布、数据库、文件或外部系统里是否真的出现结果。

三者冲突时记录为“状态冲突”，分别列出证据。禁止自行选择对产品更有利的解释。

## 5. 代码证据

原始代码可确认实现结构，但仍需区分：

- 定义存在不等于运行时已启用；
- 路由或工具注册不等于本次任务实际调用；
- 测试夹具不等于生产数据；
- 注释和变量名是线索，不自动成为业务事实；
- 运行结果、调用日志和状态变化的证据等级高于单独的口头描述。

引用代码时给出文件和行号，不复制密钥、内部凭证或无关个人数据。

## 6. 浏览取证

从最早记录开始按时间查看。只读操作包括滚动、展开、切换分类、打开已有资产/预览/历史。避免生成、重新生成、发布、购买、充值、删除或覆盖。需要登录、验证码或账号接管时暂停并交给用户。

如果外部资料确有必要，优先官方文档；第三方资料只能用于发现线索，不得作为真实内部架构证据。
